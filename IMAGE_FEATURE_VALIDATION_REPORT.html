三、架构设计决策

3.1 为什么图片走 host-side overlay 而非 document render path？

发现：render_canvas_area() 每帧从 board.elements 重写 doc.pages。 若将 ElementData::Image 插入 document，会在下一帧被覆盖丢失。
决策：镜像视频的 proven pattern — host-side image_instances: HashMap 叠加层， 在主循环 draw_image_overlay() 中独立渲染，不经过 render_canvas 的 document 路径。 render.rs 中 Element::Image 的灰色占位符保持不变（desktop 不使用该路径）。

3.2 全局唯一拖拽守卫机制

// IntegratedApp 字段
active_drag: Option<(egui::Id, HitZone)>

// 每帧调用 — 视频和图片共享同一个守卫
let new_rect = interact.update(ctx, &mut self.active_drag);

// RectInteraction::update 内部逻辑：
//   1. pointer_pressed 且命中非Outside → 尝试 claim（active 为 None 时才成功）
//   2. pointer_down 且 active.id == self.id → apply_drag(delta)
//   3. pointer_released → 释放守卫
//   4. 设置对应 CursorIcon

3.3 视频回归保证

Pause/Mute 按钮行为完全不变：在委托给 RectInteraction::update() 之前， 先用 pause_rect/mute_rect 做一次独立的 contains() 判断。 若指针在按钮上则跳过 update()（返回 None），直接执行 toggle_paused/toggle_muted。
10 个 video_player 原始测试全部通过，证明 FFmpeg 解码管线未受影响。

四、端到端数据流

用户点击「🖼 图片」
  │
  ▼
[EditApp] image_pick_requested = true
  │
  ▼  (同一帧 Prepare 分支)
[IntegratedApp] request_image_pick(ctx)
  │  └─ std::thread::spawn || rfd::FileDialog::new().pick_file()
  │     └─ 结果写入 Arc<Mutex<Vec<PathBuf>>> (pending_images)
  │     └─ ctx.request_repaint()
  │
  ▼  (下一帧)
[IntegratedApp] consume_pending_images(ctx)
  │  └─ 取出 pending_images → 对每条路径调用 insert_image_from_path(path, ctx)
  │     └─ 生成 key = "img_{timestamp}_{index}"
  │     └─ 计算 default_overlay_rect() (画布中心, 320×240)
  │     └─ 插入 image_instances[key] = ImageInstance { path, world_rect: Some(r), user_rect: None }
  │
  ▼  (每帧)
[IntegratedApp] draw_image_overlay(ctx)
  │  ├─ 遍历 image_instances
  │  ├─ world_rect 计算（同视频：canvas_offset + user_rect 或 default）
  │  ├─ 纹理懒加载：path ∉ image_textures?
  │  │     └─ std::fs::read → image::load_from_memory → to_rgba8 → ColorImage → ctx.load_texture
  │  │     └─ 缓存到 image_textures[path] = TextureHandle
  │  ├─ painter.image(tex_id, rect, Color32::WHITE)  // 绘制图片
  │  └─ RectInteraction::new(id, rect).update(ctx, &mut active_drag)  // 8方向交互
  │     └─ RectInteraction::draw_overlay(painter)  // 边框 + grip 高亮

七、手动测试建议（运行后逐项验证）

  1. 插入流程：备课模式 → 点击「🖼 图片」→ 弹出文件选择器 → 选择 PNG/JPEG/GIF/BMP/WebP → 图片出现在画布中央
  2. 基础交互：点击图片 → 显示蓝色边框 + 8 个 grip → 拖拽内部移动位置
  3. 8 方向缩放：分别拖拽 4 个角（对角变化）、4 条边（单向变化）→ 确认宽高独立变化
  4. 最小尺寸保护：将图片缩放到极小 → 确认卡在约 40×30 不再缩小
  5. 多图独立性：插入第 2 张图片 → 两张图片各自有独立边框/grip → 同时操作互不干扰
  6. 无多余按钮：选中图片时确认没有暂停 ⏸ / 静音 🔇 按钮（与视频区分）
  7. 视频回归：插入视频 → 暂停/静音按钮正常显示和工作 → 8 方向缩放/拖拽行为与修改前一致
  8. 跨模式持久：备课模式插入图片 → 切换到上课模式 → 切回备课 → 图片仍在
  9. 快捷键：按 I 键 → 弹出图片文件选择器（与 V 键弹视频选择器对称）
  10. 纹理缓存：插入同一张图片两次 → 第二次应瞬间显示（复用缓存纹理）

八、已知限制 & 后续优化方向

  • ENBX 导出暂不支持：当前 image_instances 存储在内存（host-side overlay），未写入 document model。 保存为 .enbx 时图片元素不会持久化。后续可在 sync_path_images() 中将 image_instances 同步到 doc.pages[].elements 作为 ElementData::Image。
  • keep_aspect 未实现 UI 开关：模型层 ImageElement.keep_aspect: bool 已存在， 但当前图片交互始终允许自由变形（与视频一致）。未来可在右键菜单或属性面板中添加「锁定比例」开关。
  • 删除操作：当前无法通过 UI 删除已插入的图片。后续可添加 Delete 键消费或右键菜单。
  • Z-order：多图/视频混叠时的层级顺序由 HashMap 迭代顺序决定（不稳定）。可增加 z-index 字段。
