## 视频进度条拖动卡顿修复（drafftink-desktop / video_player.rs + app.rs）

- 用户反馈：播放视频时拖动进度条「还是很卡」（此前已有 16ms UI 节流 + 非阻塞 reaper + pending 合并，仍未解决）。

### 根因（两层叠加）
1. **seek() 并非真非阻塞**：`AudioPipeline::try_new` 每次都跑 `probe_audio()`——在 UI 线程同步起 ffprobe 子进程并 `.output()` 等待（Windows 上 50~300ms）。旧进程虽交后台 reaper，但音频探测阻塞在 UI 线程。
2. **拖动期间进程重启风暴**：UI 每 16ms 节流发真实 seek + 播放器内部「首帧到达 → pending_seek 立即再重启」链式循环 → 整个拖动期以首帧延迟为周期不停杀/起 2 个 ffmpeg 进程 + 4 个线程，每次都伴随 UI 线程 ffprobe → CPU 打满、掉帧。

### 修复
- **app.rs（UI 层）**：拖动期间零真实 seek——只更新 `seek_target_ms`/`current_ms`/光标（廉价反馈）；松手时一次精确 seek（单击进度条同路径，仍即时）；拖动开始 `begin_scrub()` 冻结画面；取帧（try_recv+纹理更新）用 `inst.seeking` 门控实现拖动期间画面冻结。删除 `SEEK_THROTTLE_MS`、`last_seek_request_ms`、`std::time` import。
- **video_player.rs（缓存音轨探测）**：`VideoPlayer` 加 `audio_src: Option<SrcAudio>`（new 时 ffprobe 一次）；`AudioPipeline` 拆出私有 `try_new_with_src`/`build`（`try_new` 删除，无调用方）；`seek()` 用缓存重建音频管线，UI 线程零 ffprobe 等待。

### 顺带修复（同链路上的既有红测 seek_restarts_and_decodes）
- **根因**：解码参数从未含 `-progress`，而 `-loglevel error` 又压掉 stats 行 → ffmpeg 永远不输出 `out_time_ms` → `poll_progress_ms()` 恒 None（真实运行中进度条也从不前进）。
- **修复**：`ffmpeg_decode_args` 在 `realtime=true` 时追加 `-nostats -progress pipe:2`（键值对进度写 stderr，由既有 drain_progress 线程解析）；`VideoPlayer` 加 `progress_base_ms`（输入级 `-ss` 重启后 ffmpeg 从 0 计时，`poll_progress_ms` 叠加基准折算绝对位置，循环播放对 duration 取模）；`seek()` 记录基准。

### 验证
- `cargo check -p drafftink-desktop --offline` 0 错误；clippy --all-targets 本 crate 0 警告。
- `cargo test -p drafftink-desktop --offline`：**47 过 / 0 败**（修复前 46 过 / 1 败，既有红测转绿，无退化）。
- 既有 `drafftink_cosmos::test_rotation_system_basic` 失败与本改动无关（未触碰 cosmos）。

### 关键经验（shell-out ffmpeg 架构）
- `out_time_ms=` 只出现在 `-progress` 输出里，stats 行（`frame=... time=...`）不含该字面量；`-loglevel error` 下两者都没有。
- 输入级 `-ss`（放在 `-i` 前）会让输出时间戳从 0 重新计起，进度需加 seek 基准偏移。
- UI 线程上任何 `Command::output()`（同步等子进程）都是卡顿源；探测类结果（音轨、时长、尺寸）应缓存复用，源不变就不必重探。
