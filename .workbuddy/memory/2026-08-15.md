## drafftink-desktop 视频集成（V 键测试视频 + ENBX 内嵌视频叠加层）

### 关键决策：放弃 ez-ffmpeg，改为直接调用 ffmpeg.exe
- **根因**：仓库内置 FFmpeg 是 **2026-07-03 git master 开发版**（avcodec-63/avutil-61）。`ez-ffmpeg 0.17.2` 传递依赖 `ffmpeg-next 8.1.0` + `ffmpeg-sys-next 8.1.0`，其源码硬编码旧版 `AVCodec` 字段（supported_samplerates/sample_fmts/ch_layouts）与旧 side-data 枚举 → 编译期报 `E0609 no field supported_samplerates` / `E0004 non-exhaustive patterns`，**ABI 根本不兼容**，无兼容版本可降级/升级。
- **方案**：在 `crates/drafftink-desktop/src/video_player.rs` 用 `std::process` 驱动本地预编译 `third_party/ffmpeg/bin/ffmpeg.exe`：
  1. `ffprobe.exe -of json` 解析宽高（注意 JSON `"width": 320` 冒号后有空格，解析须 `trim_start()` 再取数字——曾因未 trim 导致全部解码失败）；
  2. `ffmpeg -hwaccels` 列出本机可用硬件加速，按 `qsv→d3d11va→dxva2→软解` 选首个能出首帧者（`-frames:v 1` 探测）；
  3. 后台线程 `-f rawvideo -pix_fmt rgba pipe:1 -re` 逐帧读取（`-re` 实时节奏，`-stream_loop -1` 循环），经 `sync_channel(8)` 送 UI；`Drop` 杀子进程 + `join` 线程优雅退出；失败不 panic。
- 内嵌视频资源写成 `*.bin` 临时文件，`ffprobe` 对未知扩展名**按内容探测**仍可用（已实测 h264/宽高/帧率识别正常）。

### 文件改动

## drafftink-desktop 视频：智能降维打击优化（解码端自适应缩放）

### 背景与做法
- 用户担心 4K 视频单帧 RGBA ≈ 33MB、缓冲堆积导致内存爆炸 + GPU 3D 占用高/卡顿。
- 在 `video_player.rs` 的 `new_with_max_dim()`（除 `new()` 外新增，默认 max_dim=1920）实现：
  - `ffprobe` 拿源宽高 → `base_scale = min(1920/w, 1920/h, 1.0)`（绝不放大）；
  - `base_scale<1.0` 时向 ffmpeg 注入 `scale=out_w:out_h,format=rgba` 滤镜，**解码端直接输出缩小后的 RGBA**（单帧降到 ~8MB），而非仅渲染端缩放。
  - 引入 `Dims{src_w,src_h,out_w,out_h}` 结构避免 `pick_backend/backend_works/ffmpeg_decode_args` 参数过多（clippy `too_many_arguments`）。
  - `VideoPlayer` 暴露 `pub base_scale` 与 `pub user_scale`（手势缩放，默认1.0）+ `set_user_scale()`；`app.rs::draw_video_overlay` 按 `user_scale` 以中心缩放；`=`/`-` 键整体缩放。
  - 帧通道由 `sync_channel(8)` 改为 `sync_channel(1)`（背压，防缓冲堆积）；逐帧 `Vec` 用 `std::mem::take` 移动代替 8MB `clone`。
  - 降维管线全后端失败 → 自动回退原分辨率 + `log::warn!`。
- 配套测试 `decode_is_downscaled_to_max_dim`：320×240 样本 + max_dim=160 → 断言 base_scale≈0.5、帧恰 160×120、字节数正确；既有测试额外断言 320×240 时 base_scale≈1.0。

## drafftink-desktop 音频集成（cpal + ringbuf + 第二个 ffmpeg 进程）

### 架构决策
- **双进程**：rawvideo 与 PCM **无法共用同一条 stdout**（`-f rawvideo` 是独占输出封装，裸流无帧边界可解复用）。`pipe:3` 方案在 Windows 下 `std::process` 无法稳定传句柄。故为音频起**独立第二个 ffmpeg 进程**：`-vn -sn -dn -ar <dev> -ac <dev> -f <f32le|s16le> pipe:1`。故障隔离，零平台特化。
- **格式协商方向 = 声卡 → ffmpeg**：读 `device.default_output_config()`，再命令 ffmpeg 重采样对齐。Rust 侧因此**没有任何重采样/混声道/位深转换代码**，回调只剩一次 memcpy。
- **刻意不加 `-re`**：音频节奏由声卡回调（硬件时钟）决定；ring + 管道背压已把 ffmpeg 限在「刚好领先」。加 `-re` 会让缓冲长期贴近空 → 调度抖动即欠载爆音。

### API 事实（版本敏感）
- **cpal 0.15.3**：`SampleFormat` 是 `I8/I16/I32/I64/U8/U16/U32/U64/F32/F64`，**没有 S16LE 这种命名**；映射 `I16→s16le`、其余→`f32le`。`Stream::pause()` 返回 `PauseStreamError`、`play()` 返回 `PlayStreamError` —— **类型不同**，直接写 `if p { s.pause() } else { s.play() }` 必得 **E0308**；须各自 `.err().map(|e| e.to_string())`。
- **ringbuf 0.3.3**：`HeapRb::<u8>::new(cap).split() -> (HeapProducer, HeapConsumer)`；`push_slice(&[u8])->usize`、`pop_slice(&mut [u8])->usize`。
- **ffprobe 陷阱（实测）**：`sample_rate` 是**带引号字符串** `"44100"`，而 `width`/`channels` 是裸数字 → 原 `parse_u32` 直接失效（有音轨被误判为无音频）。已让它容忍可选引号 + 加回归测试。`avg_frame_rate` 是有理数串 `"30000/1001"`，需 `parse_fps` 拆分。

### 同步策略：字节时钟 + skip/pad 微修正（不用 av_seek_frame）
- `av_seek_frame` 是 libav* **C API**，shell-out 架构下无 in-process `AVFormatContext`，根本拿不到；等价物只有「带 `-ss` 重启进程」（100–300ms + 必然静音），为几十 ms 偏差重启本末倒置。
- 主时钟 = `frames_shown / fps`（UI 帧驱动）；从时钟 = `(played - skipped) / bytes_per_sec`（声卡实际消耗字节）。`AudioClock` 用 3 个 `AtomicU64`：`played` / `skip`（落后→丢字节快进）/ `pad`（超前→填静音等待）。
- `SYNC_THRESHOLD_MS=150`（死区，参考人耳可察觉阈值 音频超前~45ms/滞后~125ms）、`SYNC_MAX_CORRECT_MS=1000`。**修正量必须对齐 `frame_bytes`**，否则左右声道错开半样本 → 声场翻转。
- 修正计算放 `audio-sync` 独立线程，UI 侧 `report_video_time` 退化成一次无阻塞 `mpsc::send`（500ms 心跳）。

### RingBuffer 容量（澄清需求原文的误算）
- 需求写「1MB ≈ 100ms」**是错的**：1MiB 在 48k/2ch/f32 下是 **2.73s**（100ms 实际只需 ~37.5KiB）。仍保留 1MiB —— **大缓冲 ≠ 高延迟**：播放位置由声卡已消耗字节定义，缓冲区是「预读」；填满后 `push_slice` 返 0 → 搬运线程睡 → 管道满 → ffmpeg 自阻塞，稳态代价只是 ffmpeg 停在原地。换来对磁盘卡顿/调度抖动的容错（100ms 在 Windows 一次调度抖动就击穿）。
- 实例化时**按 `frame_bytes` 向下取整**（6ch/f32 时 1048576%24=16 → 容量 1048560），否则环绕处半帧错位。
- 三重背压：ring 满→sleep 5ms；不读→OS 管道(4–64KB)满→ffmpeg 阻塞 write；暂停→干脆不读。

### 状态联动
- **暂停不重启进程**（否决需求原文建议）：**混音器句柄持有者是 cpal 不是 ffmpeg**，ffmpeg 只往 stdout 写字节、从不碰音频设备；要释放设备用 `stream.pause()`（WASAPI 下 `IAudioClient::Stop`）。双保险：停流 + 置 `paused` 标志（回调仍被调则静音且**不推进 played**）→ 恢复后天然对齐。
- **静音只改一个原子布尔**，且清零发生在 `pop_slice` **之后** → 仍消耗数据、仍推进时钟 → 静音 30s 后取消得到第 30s 的声音（符合直觉，无需同步补偿）。
- 欠载补静音 `out[n..].fill(0)`，**不重复上一段**（否则可听见「咔哒」）。
- `Drop` 显式编排：`stop=true` → `stream.pause()`+drop → `child.kill()+wait()`（**wait 必调，否则僵尸进程**）→ drop `sync_tx` 唤醒 recv → join 3 线程。不依赖字段析构顺序（防「回调仍跑而 Consumer 已回收」）。

### 零拷贝 unsafe
- 回调给 `&mut [i16]/[f32]`，ring 里是 `u8`：用 `slice::from_raw_parts_mut(data.as_mut_ptr().cast::<u8>(), size_of_val(data))` 重解释直达声卡缓冲。**不能用 `mem::transmute`**（对不同长度的切片类型是 UB，胖指针长度字段语义被错误保留）。安全性：两类型无内部不变量、对齐 2/4B 严于 u8、小端布局与 s16le/f32le 逐字节一致、全零恰为静音。`skip` 分支复用 `out` 当丢弃暂存区，连丢弃都不额外分配。
- `fill_pcm` 硬实时约束：全程无锁/无分配/无系统调用/无阻塞，只有原子 + memcpy。

### 顺带修掉的既有 bug
1. **致命**：`let paused_flag = stop.clone();` —— paused 与 stop **共用同一 Arc<AtomicBool>**，第一次暂停即等于停止，解码线程直接退出、恢复后永久冻结。改为 `Arc::new(AtomicBool::new(false))`，加回归测试 `pause_then_resume_keeps_decoding`。
2. **UI**：暂停按钮圆心在 `rect.max`（右**下**角）与 resize grip 命中区重叠。移到顶边，左侧新增静音按钮（仅 `has_audio()` 时绘制）；`Hit::Button` 拆为 `Hit::Pause`/`Hit::Mute`；快捷键 Space 暂停 / **M 静音**。
